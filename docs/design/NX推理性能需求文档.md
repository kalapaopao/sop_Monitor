## 一、目标

**一台 Jetson Xavier NX 服务 1–4 个工位：每路视频同时跑「联合 OBB + RTMW 骨架」，
输出可喂给 TCN 的骨架流，并为通讯与存储留出资源余量。**

```
1–4 路摄像头 → 硬解 → OBB(螺丝批1 / 螺丝批2 / 手 / 人) + RTMW(133 点)
            → [待接入] TCN 时序判定 SOP 步骤
            → [待接入] MQTT/HTTP 通讯 + 本地存储
            → [待规划] 工位屏幕：良率 / 产量 / 工时 / 纠错提醒
```

- 各工位**视觉前端完全一致**，只有 TCN 判定的 SOP 步骤因工种而异。
- **4 路是最基础的生产配置**；上限就是 4 路（2026-10-21 决策，不做 6/8 路）。
- **当前阶段以"做出 Demo"优先**，架构允许先笨重、后收缩（见第九节）。

### 1.1 优先级（2026-10-22 用户明确）

| 等级 | 内容 | 说明 |
|---|---|---|
| **唯一必须** | **SOP 装配步骤识别** | 只要这个能做出来，其余都是锦上添花 |
| **基本要求** | **良率、产量等基础统计** | 必须有，但服务于 SOP 识别，不是独立目标 |
| **基本要求** | **系统通用、厂家可自助训练** | 换产品不改程序；厂家能自己采数据、训练模型（D2） |
| **商业目标** | **模型训练服务可收费** | 厂家自训练效果不如我方，可提供付费训练服务（D3） |
| **锦上添花** | 工时统计、报表、历史趋势、多 NX 协同、产品追溯 | 有余力再做，不为它们增加系统复杂度 |

**判断依据**：SOP 识别是系统存在的理由；统计是产线管理的基本需要；
通用性决定产品能否复制到多家工厂（否则每家都要配工程师，卖不动）；
其余功能每增加一项都会让系统更复杂、更难维护，与"往简单做"冲突。

**推论**：
- 性能优化服务于"让 SOP 识别跑得动"，不服务于跑分（见 7.1）。
- 纠错提醒必须有（形态 ②，见 3.5）；产品追溯可以没有（形态 ③，暂不做）。
- 一台 NX 服务 4 工位，不引入第二台 NX（见第九节）。
- **代码里不能硬编码任何具体产品的 SOP 步骤顺序**（见 4.2）。

## 三、工位屏幕与上位机（新需求，2026-10-22）

### 3.1 需求描述

每个工位上方有一块屏幕，显示该工位的**良率、产量、工人工作时长**等参数，
并对工人操作做**纠错提醒**（"不要让工人犯错"的提示界面）。

即：**1 个工位 = 1 块屏幕 + 1 台上位机**。

### 3.2 关键判断：屏幕 ≠ 上位机

这是本需求最容易搞混、也最影响成本的一点：

| 职责 | 归属 | 算力需求 |
|---|---|---|
| 显示良率 / 产量 / 工时 | 屏幕终端 | **接近零**（拉 HTTP 渲染网页） |
| 现场纠错提醒 | 屏幕终端（订阅 MQTT） | 低（刷屏 + 响铃） |
| 扫码 / PLC / 工装状态 / 本地队列 / 断网缓存 | 上位机 | 中等（需要本地业务逻辑） |

**决定要不要一台上位机的，不是"有没有屏幕"，而是"工人要不要在这块屏上操作"。**

### 3.3 硬约束（已实测）

| 项 | 实测 |
|---|---|
| NX 物理显示输出 | **仅 1 × HDMI（已接 1440×900）+ 1 × DP（disconnected）** |
| 结论 | **NX 无法驱动 4 块独立屏幕**，这是物理接口限制，不是算力问题 |
| 空闲 CPU | 84.6% idle（但 4 路推理时 GPU 已占 68–98%） |
| 内存 | 6848 MiB，空闲可用约 4.3 GB |

因此 **"让 NX 同时驱动 4 块工位屏" 这条路直接排除**，不是优化问题。

### 3.4 三种屏幕形态（供后续收缩时选型）

| 形态 | 内容 | 延迟要求 | 终端成本 | NX 负担 |
|---|---|---|---|---|
| **① 纯统计展示** | 良率/产量/工时，数据来自中央 SQLite | 秒级，不敏感 | 最低（安卓盒/kiosk 网页） | **零** |
| **② 统计 + 实时纠错** | 额外在错误动作瞬间弹提醒 | **200–500 ms，敏感** | 低 | **只发 MQTT 小消息**，不渲染 |
| **③ 统计 + 纠错 + 交互** | 额外支持扫码、确认、呼叫 | 提醒敏感、统计不敏感 | 需一台像样主机 | 只发消息 |

形态 ②/③ 的数据源是 **NX 的 TCN 判定结果**，走 NX 本地 MQTT Broker
（链路已在 `当前系统架构.md` 第 2 节定义）。**NX 只发消息，不画 UI**——
无论哪种形态，NX 都不承担渲染。

### 3.5 形态已定：② 统计 + 实时纠错

**2026-10-22 决策：确定采用形态 ②。** 判断依据：

- **SOP 装配步骤识别是系统的核心价值**，不是附属功能。
- **工人当场没做该步骤，必须当场纠错提醒** —— 这直接把"事后统计"排除掉了。
- 统计数字（良率/产量/工时）保留，但它是**辅助展示**，不是主目标。

对应到 3.4 的表：

| 项 | 决策 |
|---|---|
| 屏幕内容 | 纠错提醒（主）+ 良率/产量/工时（辅） |
| 延迟要求 | **200–500 ms，敏感** |
| 通讯 | **MQTT**（NX 本地 Broker），不走 HTTP 轮询 |
| 终端 | 需能订阅 MQTT + 刷屏 + 响铃；**不需要扫码/PLC** |
| NX 负担 | 只发 MQTT 小消息，**不渲染画面** |

**形态 ③（扫码/交互）降级为"暂不需要"**：只有出现产品追溯需求时才重新评估，
不提前为它搭架子（见 9.1 的"从简"原则）。

## 四、通用性与厂家自助训练（2026-10-22 新增）

### 4.1 三条核心需求

| 编号 | 需求 | 含义 |
|---|---|---|
| **D1** | **先采数据、再定 SOP** | 采集大量工人操作数据 → 数据化 → 找出**出现频次高、重复性强的动作**，再放进 TCN |
| **D2** | **系统必须通用** | 部署完成后，**厂家能自己采集数据、自己训练模型**，我方不介入每一次换型 |
| **D3** | **提供训练服务（收费）** | 厂家自训练效果通常不如我方（非专业人员），我方提供**付费的模型训练服务** |

### 4.2 关键区分：通用性是目的，不是"禁用某种技术"

**不是禁止状态机。** 真正的要求是：

> 系统本身要写得通用 —— 换产品、换 SOP 步骤时，**不需要改程序**。

状态机只是实现手段之一。它的问题**不在状态机本身**，而在于"把步骤顺序硬编码进代码"
这种做法会让每次换型都要我方改代码。**只要步骤定义是数据驱动、可配置的，用什么技术实现都可以。**

| 做法 | 是否可接受 | 原因 |
|---|---|---|
| 步骤顺序硬编码在 C++ 里 | ❌ | 每次换型都要改代码、重编译、重新部署 |
| 状态转移图写在**配置文件/数据库**里，程序通用 | ✅ | 换型只改配置，程序不动 |
| 完全由 TCN 从数据里学顺序 | ✅ | 换型只需重新训练模型 |

**判断标准只有一条：换产品时要不要改程序。** 不改程序 = 通用，符合 D2。

### 4.3 为什么系统要通用（D2）

```
当前做法（不通用）：
换产品 → 新工艺路线 → 我方写代码 → 重编译 → 部署 → 收售后费（人力换钱）

目标做法（通用）：
换产品 → 厂家自己在现场采数据、训练模型 → 换模型文件 → 上线
        └─ 效果不好？→ 购买我方的训练服务（D3）
```

通用化的价值不只是省我方人力，更是**产品可复制**：
一套系统能卖给多家工厂，而不用为每家配一名工程师。

### 4.4 自助训练与付费服务（D3）

| 角色 | 能力 | 结果 |
|---|---|---|
| 厂家（自助） | 用我方提供的工具采数据、点训练 | 能跑通，但**效果通常不如专业调优** |
| 我方（付费服务） | 专业标注、模型选型、超参调优、验收 | 效果更好，**可收费** |

这不是矛盾，而是**分层产品**：

- **软件卖通用能力**（能自己训练，不被绑定）
- **服务卖效果**（训练得更好，愿意付费）

**前提**：自助训练必须在没有我方参与的情况下**真的能跑通**。
否则"厂家自助"只是话术，最终仍是我方救火。

### 4.5 D1 的方法论：先找"高频重复动作"

**不是所有动作都值得建模。** 优先挑：

- **出现频次高**：每个工件都做，样本量充足
- **重复性强**：动作模式稳定，个体差异小（如"取螺丝批""拧第二颗"）
- **可区分**：与其他步骤在骨架轨迹上有明显差异

低频、随机、因人而异的动作**不纳入 TCN**——数据不够，硬学只会得到低 F1。

### 4.6 数据采集要求

| 项 | 要求 | 状态 |
|---|---|---|
| 采集通道 | 复用 NX 现有的骨架输出（P1 契约） | **待建** |
| 采集内容 | 133 点骨架 + 时间戳 + 工位 ID + 标签 | **待建** |
| 采集规模 | 每个动作类别需要多少样本 | **未知（见 Q7）** |
| 标注方式 | 谁标、怎么标（人工？半自动？） | **未知（见 Q7）** |
| 存储位置 | 中央 TL3576 的大分区（106 GB） | 已具备 |
| 隐私 | 骨架点不是人脸，但仍是工人行为数据 | 需确认合规要求 |

**关键约束**：采集必须在**不增加 NX 负担**的前提下进行——
这正是 P1（TCN 输出契约）要先做的原因：有了结构化输出，采集就是记日志。

### 4.7 对系统设计的影响

1. **TCN 训练必须能离线完成**，不占用 NX 推理资源。
2. **模型文件要能热替换**（换产品时换 `.engine`，不是重编译程序）。
3. **训练工具必须有界面**，厂家不是工程师（当前 `project/tcn_usescrewdriver*`
   是脚本形态，**不满足 D2**，需要产品化）。
4. **步骤定义要数据驱动**：顺序可以写在配置/数据库里，也可以由模型学，
   但**不能硬编码进源码**。
5. **SOP 步骤的可配置性**：新增/删除/调整步骤顺序，应当是配置操作或重新训练，
   而不是改 C++ 重编译。

### 4.8 商业模式与交付边界（D3）

| 交付物 | 内容 | 谁付费 |
|---|---|---|
| **软件（一次性）** | 推理系统 + 采集工具 + 训练工具 + 上位机 | 买软件 |
| **厂家自助训练** | 厂家自己采数据、自己训练 | 免费（含在软件里） |
| **专业训练服务** | 我方标注、调参、验收，效果更好 | **按项目收费** |
| **换型支持** | 厂家换产品时可选我方介入 | **按次收费** |

**关键设计约束**：自助训练必须**真的能跑通**。如果厂家拿工具跑不出可用模型，
"D3 卖服务"就变成"必须买服务"，这是**产品缺陷**而不是卖点——
会让客户觉得被绑架，反而更难成交。

**取舍**：宁可自助训练的效果只是"能用"（比如 F1 0.75），
也要保证它**独立可完成**；专业服务卖的是"从 0.75 到 0.9"的增量。

### 4.9 与现有路线的关系

| 现有条目 | 调整 |
|---|---|
| P1 SOP 输出契约 | **升级为最高优先级**——它同时是"纠错"和"采集"的前置 |
| P2 模型接入 | 增加"模型可热替换"要求 |
| 旧 N6「SOP 状态机实现」 | **不再是"不做"**——状态机本身可用，但步骤定义必须可配置、不改程序 |
| 新增 P0 数据采集阶段 | 见 7.2 |

## 五、基线（已确认）

### 5.1 硬件

Jetson **Xavier NX**（非 Orin）· JetPack 5.1.1 · CUDA 11.4 · TensorRT 8.5.2 ·
OpenCV 4.5.4 · 6 核 · 6848 MiB · MODE_20W_6CORE（常报 `Over-current` 降频）。

### 5.2 模型

| 模型 | 引擎 | 输入 | 精度 |
|---|---|---|---|
| 联合 OBB（4 类） | `models/batch_20261020/obb_640x384_b1_4.plan` | 动态 `(-1,3,384,640)` | FP16 混合 |
| 联合 OBB（方形） | `models/batch_20261020/obb_640x640_b1_4.plan` | 动态 `(-1,3,640,640)` | FP16 混合 |
| RTMW 133 点 | `models/batch_20261020/rtmw_b4.plan` / `rtmw_b2.plan` | 固定 `(4\|2,3,256,192)` | FP16 混合 |

- **不是 int16**——int16 不是 TensorRT 的精度类型。证据在 `scripts/build/build_batch_engine.py`
  （`BuilderFlag.FP16` + 主干 `OBEY_PRECISION_CONSTRAINTS`，检测头保持混合）。
  引擎逐层精度**无法内省**，结论来自构建脚本而非引擎内部。
- 部署硬约束：`.plan` 必须与 `libsop_silu_plugin.so` 一起拷，否则反序列化失败。

### 5.3 性能

口径：`scripts/run.sh` 启动，前 5 s 预热不计入 `steady_job_hz`。

| 配置 | 每路 Hz | 合计 | 状态 |
|---|---:|---:|---|
| **4 路** | **19.0** | 76 | 唯一有优化空间的配置 |
| 3 路 | 22.3 | 67 | 未撞源上限 |
| 2 路 | 25.0 | 50 | 已撞 25 fps 源上限 |
| 1 路 | 25.0 | 25 | 已撞 25 fps 源上限 |

- 延迟：4 路 `pose_age_p95 = 120 ms`，只有 40 / 80 / 120 三档（结构性），93% 滞后 2–3 帧。
- 资源：GPU 68–98%（均值 85%，**未跑满，存在等待**）、内存 3799 / 6848 MiB。
- 单组耗时、批处理效率、逐项对照的完整数据见 `docs/reports/BATCH_REPORT_20261020.md`。

## 六、瓶颈与已证伪项

一组 4 帧共 **52.52 ms**：OBB 31.29（59.6%）+ RTMW 21.23（40.4%）+ 上传 4.02（7.7%）。
**两个引擎占 99.8%，后处理只占 2.3%**——优化后处理没有意义。

线性拟合 `t(n) = 固定开销 + n × 单帧成本`：OBB 7.09 ms/帧 + 2.94 ms 开销；
RTMW 4.38 ms/人 + 3.69 ms 开销；**合计固定开销 6.63 ms，占一组 12.6%**。

**已实测证伪，勿重复尝试：**

| 假设 | 实测结果 |
|---|---|
| SimCC 解码是 CPU 瓶颈 | 占 2.3%，不是 |
| `cv::minMaxLoc` 替代手写扫描 | 更慢 |
| 调 `--batch-wait-ms`（0 / 5 / 10） | 完全无影响 |
| 降低 batch 提速 | 全部更慢 |
| `rtmw_b2` 替代 `b4`（4 路） | b4 更优 |
| `--workers 2` 多 context 并行 | 参数已删除，`workerCount` 硬编码为 1 |
| `INTER_AREA` 缩放 | 慢 16 倍 |
| 显示路径优化 | 非生产路径，不做 |

## 七、目标与路线

### 7.1 先说清楚"够不够"

**在 TCN 采样率确定之前，不设 Hz 目标。** 理由：

- 1 / 2 路已撞 25 fps 源上限，任何优化都不会让它们更快；
- 4 路 19 Hz 若已满足 TCN（常见判定窗口下 10–15 Hz 足够），**性能上就没有问题**，
  剩余价值只是"省出资源给通讯与存储"。

**Q1（唯一阻塞项）：TCN 需要多高的骨架采样率？**
这是决定"要不要冒险做 INT8"的唯一问题。≥22 Hz 才需要考虑量化。

### 7.2 路线优先级

主线是**先让系统通用 → 厂家可自助训练 → 再谈纠错效果**，性能优化排在最后
（对应第 4 节的 D1/D2/D3）：

| 优先级 | 事项 | 说明 |
|---|---|---|
| **P0** | **数据采集通道** | 复用 P1 的骨架输出，落盘为可训练的数据集。**没有数据，后面全部空谈** |
| **P1** | **SOP 输出契约** | 骨架流格式 / 时间戳口径 / 缺失值 / 工位 ID。**采集、训练、纠错共同的前置** |
| **P2** | **动作筛选与标注** | 从采集数据中找出高频、重复性强的动作（4.5 节），标注成训练集 |
| **P3** | **训练工具（厂家自助）** | 有界面、能离线训练、出模型文件。**满足 D2：厂家自己点，我方不改代码** |
| **P4** | **模型接入与热替换** | 换产品 = 换模型文件，不重编译程序 |
| **P5** | **工位身份映射** | YAML 加 `station_id`，纠错提醒才知道发给哪个工位 |
| **P6** | **MQTT 接入（纠错闭环）** | NX 接本地 Broker，判定结果回传，工位屏幕当场弹提醒（见第九节） |
| P7 | 消除组内固定开销 6.63 ms | 提交/取结果分离，理论 +14%；约 20–30 行，需双缓冲（约 5.5 MB） |
| P8 | INT8 量化 | 仅当 Q1 要求 ≥22 Hz 才做，高风险，需标注集验收 |
| P9 | RTMW 固定开销 3.69 ms | `rtmw_b4` 在 1 路时 3/4 算力在算填充数据 |

**顺序理由**：P0–P6 是"通用系统 → 数据 → 自助训练 → 纠错"的完整闭环；
P7–P9 只是省算力。**在闭环未跑通前，性能优化没有可验证的收益对象。**

**关于 P3 的硬要求（来自 D2）**：训练工具不能是脚本。厂家不是工程师，
必须能"选数据 → 点训练 → 拿模型文件"。当前 `project/tcn_usescrewdriver*`
是实验脚本形态，**不满足交付要求**。

**关于 D3 的分层定位**：
- P3 保证**厂家自助能跑通**（软件能力，卖的是通用性）
- 自助效果不好时，我方提供**付费训练服务**（专业标注 + 调参 + 验收）
- 二者不冲突：软件不绑定我方，服务卖效果

> ⚠️ **TCN 的已知风险**：当前最好 F1 只有 **0.6620**（183 维特征，单视频 08，二分类"是否在用螺丝批"），
> 直接上线会误报/漏报。纠错提醒一旦误报会干扰工人，误报率高比不做更糟。
> **F1 需要先达到可接受水平**，这一条应在 Demo 前确认（见第十一节 Q6）。
> 四组实验的完整对照见[技术方案](NX推理侧技术方案.md) 4.1 节。

## 九、Demo 优先策略（2026-10-22 决策）

### 9.1 决策

**系统往简单的方向做。一台 NX 服务 4 个工位，每工位一台 TL3576，把 SOP 纠错闭环先跑通。**

三条原则：

1. **SOP 装配步骤识别是重点**，其他（统计报表、多 NX、复杂终端）都是配角。
2. **能少一个设备就少一个**：不提前为"以后可能需要的形态"搭架子。
3. **先跑通再收缩**：Demo 接受"每工位一台 TL3576"的笨重，但**不引入第二台 NX**。

### 9.2 为什么是这个形态

| 理由 | 说明 |
|---|---|
| 纠错是刚需 | 工人当场没做该步骤要当场提醒 → 必须有低延迟 MQTT 通道，形态 ② 已定（3.5 节） |
| 现有架构已完整 | `当前系统架构.md` 三条链路已定义：NX↔中央管理 / NX↔工位实时 / 工位→中央 HTTP。照用即可，改方案成本高于先跑通 |
| 硬件已在手上 | 中央 TL3576（192.168.1.20）已部署验证；工位 TL3576 是现成设备 |
| **1 台 NX 够用** | 4 路 19 Hz（5.3 节），若要满足 TCN 10–15 Hz 的采样率仍有富余。**没有理由上第二台 NX** |
| 从简优先 | 多 NX 会带来协同、时钟同步、状态一致性等一整套问题，与"往简单做"冲突 |

### 9.3 Demo 形态

```
NX（1 台，推理 + TCN + 本地 MQTT Broker）
  ├─ 工位 1：TL3576 上位机（屏幕显示纠错提醒）
  ├─ 工位 2：TL3576 上位机
  ├─ 工位 3：TL3576 上位机
  └─ 工位 4：TL3576 上位机
        │
        └─ 中央 TL3576（192.168.1.20:8000）：SQLite + React 网页 + 图片存储
```

职责边界：

| 节点 | 负责 | 不负责 |
|---|---|---|
| **NX** | 推理 + TCN 判定 + 发 MQTT 消息 | **不渲染画面**（3.3 节：物理上只有 1 HDMI） |
| **工位 TL3576** | 屏幕显示 + 响铃提醒 + 本地缓存 | 不做视觉推理 |
| **中央 TL3576** | 统计、报表、图片留存 | 不参与实时纠错链路 |

### 9.4 后续收缩方向（不在 Demo 范围）

Demo 跑通并拿到真实数据后再逐项评估，**每项独立决策、独立实施**：

| 收缩方向 | 前提 | 收益 |
|---|---|---|
| 屏幕改用轻终端（kiosk 网页） | 确认不需要扫码/PLC | 省掉大部分工位 TL3576 |
| 工位上位机功能上移/下移 | 明确职责边界后 | 减少设备数量 |
| **多 NX 协同** | 工位数**超过 4** 时 | 当前无需求 |
| NX 直连屏幕 | **不可行**（仅 1 HDMI + 1 DP） | — |

**关于多 NX**：`NX ↔ NX 通讯` 目前**没有需求驱动**。1 台 NX 管 4 个工位是既定目标（第一节），
只有工位数超过 4 时才需要第二台 NX 及其协同。当前阶段**不设计、不预留**这条链路。

### 9.5 Demo 验收边界

Demo 要证明的是**纠错链路通**，不是性能好，也不是功能全：

- ✅ 工位触发 → NX 推理 → **TCN 判定 SOP 步骤** → 结果回 MQTT → 工位屏幕**弹纠错**
- ✅ 漏做步骤时，提醒在 **200–500 ms** 内出现
- ✅ 工位 → 中央 HTTP 上传（图片 + 周期数据）
- ✅ 中央网页能看到统计数据
- ❌ **不要求**：屏幕形态的最终硬件选型、4 路满负荷下的屏幕刷新率、断网重连完备、产品追溯
