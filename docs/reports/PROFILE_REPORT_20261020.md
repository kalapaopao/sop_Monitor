# 四路性能分解与优化方向：2026-10-20

## 1. 结论与完成范围

已在实际 Xavier NX 完成同一组 03/03/07/07 视频的四路性能分解、原版对照、单引擎 CUDA Graph 对照和 Nsight 采集。
本轮只增加可选计时入口，保留当前两个模型、640×640 检测输入、192×256 骨架输入、阈值、最新帧队列和显示方式。
没有实现矩形输入、batch、GPU 后处理、INT8 或应用中的 CUDA Graph，也没有 commit/push。

**主要耗时在两个引擎的执行区间，其中 OBB 比重较大。GPU 输出回传与 CPU 后处理不是本轮首要瓶颈。**
CUDA Graph 单模型吞吐只提高约 4–5%，虽明显减少 CPU 提交耗时，仍不足以达到四路各约25次完整识别/秒。

## 2. 环境与方法

- 设备：NVIDIA Jetson Xavier NX Developer Kit，ARM64，Ubuntu20.04，TensorRT8.5.2，CUDA11.4。
- 只读功耗模式查询显示 `MODE_20W_6CORE`；部分 EMC/过流限制节点读取被权限拒绝，因此没有完整功耗上限诊断。
- 未安装软件、修改功耗/时钟、网络、桌面服务或驱动。
- 每次端到端测试40秒，前5秒预热不计入吞吐和阶段分布。四路顺序公平轮询，每路待处理最新帧容量1，旧待处理帧会被替换。
- 源视频1920×1080，03约24.975FPS，07为25FPS；每任务对检测到的人体逐个运行RTMW，再选择原规则中的最佳骨架。没有人体时不会调用RTMW。
- 两路03及两路07是文件模拟，并非四台真实RTSP摄像头。人员数量与解码格式变化会改变容量。
- CPU阶段使用steady_clock；GPU使用同stream的CUDA event。读取计时依赖原有模型完成等待，没有额外同步等待。
- GPU event引擎区间包含GPU计算、内部转换以及该区间中的调度间隙，不等于纯算术内核执行时间。
- CPU提交与GPU执行相互重叠，CPU等待也与GPU活动重叠。下表中的总计、子项和CPU/GPU值不能全部相加。
- 采集读取包含appsink等待、解码管线交付和下载，不能当作单独的硬件解码耗时；采集与推理/显示并行。

## 5. 同一份引擎的CUDA Graph对照

这些是 `trtexec --noDataTransfers` 的隔离测试，不包含视频、预处理、后处理和显示；没有将Graph接入现有应用。
普通测试使用 `--separateProfileRun`，引擎性能值来自未附逐层分析器的基准阶段。

| 模型 | 普通→Graph吞吐QPS | 增幅 | GPU执行区间ms | CPU enqueue ms |
|---|---:|---:|---:|---:|
| OBB | 85.697 → 89.859 | 4.86% | 11.668 → 11.128 | 6.491 → 0.303 |
| RTMW | 135.951 → 141.851 | 4.34% | 7.355 → 7.049 | 2.853 → 0.177 |

结论：CPU enqueue明显变短，但大部分提交工作原先已与GPU执行重叠。不能把约9ms的enqueue下降当成整条链路节省9ms。
两个Graph引擎区间相加仍约18.18ms；保持现有逐任务串行结构时，单靠Graph达不到100任务/秒所需的10ms预算。
这是隔离单引擎基准，不能直接拿QPS相加，也不能把其收益当作端到端四路收益。

## 6. Nsight与引擎结构

- Nsight成功生成 `four_headless.nsys-rep`、SQLite及CUDA API/内核/搬运统计。请求采集10秒，SQLite中首末CUDA活动跨度约8.26秒。
- 捕获到194,917个CUDA内核，26,497次自定义SiLU调用，后者总执行约601.8ms。
- OBB引擎层信息确认93个 `/act/Mul` 激活层；名称包含copy/reformat的层166个。后者包括正常拆分复制，不能全部视为冗余，也不能未经对照就归因于插件。
- 观察到Tensor Core相关卷积内核、独立SiLU和NCHW/NHWC转换，值得对原生激活、融合与格式支持做有针对性的引擎对照。
- 自定义SiLU是否导致净性能损失仍未由原生引擎对照证明；此前原生引擎构建很慢，本轮未重新构建。
- Nsight有显著采集开销：整个应用稳态约10.35Hz/路，低于无画面原版11.35Hz/路。其内核结构可用于定位，采集中的利用率及单项耗时不作为正常运行的精确容量结论。
- 普通事件计时数据与Nsight数据分开报告，没有把Nsight中的CUDA活动占比当成整块GPU的正常SM利用率。

## 7. 下一步优先顺序

1. **OBB 640×384矩形输入对照**：原1920×1080图像内容仍缩为640×360，仅减少填充；输入面积减少40%。重新导出并生成独立引擎，解码改为按实际输出形状处理。RTMW仍从原始图像裁剪。面积减少不等于耗时按比例减少，需比较小工具、人体框和骨架效果。
2. **batch=1/2/4**：分别测检测与人体裁剪批量，不强制两模型相同batch。限制凑批等待，记录每路吞吐和结果年龄，避免总吞吐提高但某路结果持续变旧。
3. **OBB融合与格式转换对照**：原生激活或更合适的插件格式可否降低实测耗时；保留现有可运行引擎，独立生成实验引擎。
4. **CUDA Graph应用集成**：隔离基准已确认可运行，适合作为减少CPU负担、改善波动的后续项，不能承担2.5倍提升目标。
5. 如果仍明显不足，评估OBB INT8、轻量RTMW/蒸馏或设备升级。涉及精度的方案必须单独验收。

不优先继续加完整推理工作线程。当前后处理与预处理也不是最值得先投入的大项。
未证明Xavier NX在当前模型和效果下可以四路各25次完整识别/秒；本轮没有更改此目标或以插值/重复显示替代完整识别。
