# 两路03＋两路07：从开头读取的四路实验（2026-10-16）

## 结论

已扩展现有实验入口，四路各自独立读取、排队和保存结果，共享一套OBB、YOLOX和RTMW，在一个推理线程中公平轮询。四宫格可以显示；当前有画面的新识别更新约3.76 Hz/路，未达到四路连续、低延迟骨架显示要求。

本轮只缩小显示副本，算法输入源仍为每路1920×1080原图。进入神经网络前按原规则预处理：OBB 640×640，YOLOX 416×416，RTMW从原图人体区域裁剪到宽192×高256。没有修改权重、引擎精度、检测阈值或关键点解码。

这是真实运行四个独立视频读取器的文件模拟，尚未连接四路摄像头或网络流。

## 架构与线程

- 一个C++进程，应用自身有6个线程：4个解码线程、1个共享推理线程、1个主显示线程。OpenCV/FFmpeg等库可能另有内部线程。
- 每路一个最新待处理任务槽，以及独立预览、结果和帧编号；推理繁忙时替换尚未开始任务，队列不无限增长。
- 推理依次执行OBB→YOLOX→RTMW；无人框时跳过RTMW，有多个框则分别推理，最终仍只显示该路最佳单人骨架。
- 上排03/03，下排07/07；默认总窗口1100×620，每格550×310。预留标签栏后原图约缩为508×286显示，保留宽高比。
- 只重绘出现新帧的格子。最终版本按最高源FPS（本次约25）合批刷新整窗，而不是随每一路发布都立即提交显示。
- 三个引擎各加载一份，由唯一推理线程调用。多开完整进程会重复加载资源，并竞争同一GPU；增加线程/进程不等于GPU算力线性增加。

流程图及联合检测方案的取舍见 [ARCHITECTURE.md](../architecture/ARCHITECTURE.md)。

## 输入与测量方式

- 同一台NX、系统可见内存6848 MB，使用已有TensorRT/OpenCV环境。
- 四路顺序：03、03、07、07；全部指定start-sec 0，从源视频开头按各自FPS定时读取。03约24.9795 FPS，07约24.9998 FPS，原图均1920×1080。
- 每组运行30秒，前5秒启动预热不计入steady_job_hz；日志/CSV保留启动段。
- 实时模式允许丢弃尚未开始任务及未消费预览帧，因此有窗口的第一条CSV可能不是frame 0；这不代表从180秒开始或跳过文件前段。无窗口组四路第一条消费帧均为0。
- 始终保留默认200 ms显示过期阈值，未放宽该值来隐藏性能不足。
- 结果年龄按各路源帧差/FPS计算，不含GTK实际呈现、远程桌面或Windows屏幕延迟。

## 测试结果

| 模式 | 每路预热后任务Hz | 骨架源时间年龄P95 | 超200ms而隐藏的预览帧比例 |
|---|---|---|---|
| 四路无窗口 | 4.759 / 4.759 / 4.799 / 4.759 | 约280 ms | 47.7–48.5% |
| 四宫格初测，每次新帧触发刷新 | 3.116 / 3.116 / 3.116 / 3.076 | 约440 ms | 72.4–74.7% |
| 四宫格合批刷新复测（最终版本） | 3.756 / 3.756 / 3.756 / 3.756 | 约360 ms | 56.6–58.8% |

合批显示复测中，四路各完成96个任务，RTMW分别调用96、96、98、99次；与先前03在180秒位置的测试不同，从开头这段人体检出更充分，计算负载较完整。没有据此验证人体框或关键点的标注准确率。

最终组各路解码750、750、751、751帧；显示消费678、680、694、686帧；替换653、653、654、654个未开始任务。主窗口实际提交716次/约30秒，约23.85次/秒；每路预览约22.6–23.1次/秒（含启动段）。显示消费率与新识别更新率必须区分。

最终组前5秒之后，四路均有骨架结果，但约57–59%的预览帧因结果超过200ms而隐藏。这是当前四路串行配置的实质限制，不能称为流畅稳定的四路实时骨架方案。放宽过期阈值会显示更老的结果，不会增加推理速度。

四路CSV检查均未发现使用未来帧结果；各路任务数接近，未发现轮询饥饿。没有做跨路身份关联、标注准确率、不同人数持续负载或长期稳定性测试。

初始两组监控系统RAM峰值3517 MB、GPU最高45.5℃；合批显示复测RAM峰值3519 MB、GPU最高44.5℃。两次监控交换区均从256 MB开始，最高仍为256 MB，未观察到本轮新增占用；这是系统级短时观察，不是每进程内存占用或长期无增长证明。

## 进程知识的实际作用

线程适合本项目当前的共享内存流水线：取流、推理、显示分别运行，帧和模型在同一地址空间传递。进程适合故障隔离、服务守护及采集与推理服务分离，但跨进程传完整帧需要共享内存或其它通信机制及同步管理。当前实验已多线程；四路识别速度不足不能简单归因于线程数量不够。

用户提出将人体检测加入OBB，形成“工具/手/人体联合检测→RTMW”：当前OBB只有screwdriver1、screwdriver2、hand，需要增加人体标注并训练，验证召回率、框范围和RTMW裁剪规则。对本轮串行探针有机会省掉YOLOX计算；对原单路并行版，RTMW改为等待OBB人体框会改变依赖关系，仍需实测速度和骨架延迟。本轮没有训练、融合或替换模型。

四路各25次新识别/秒合计需要100个任务/秒；本轮有画面观察约15个任务/秒总量，存在较大差距。后续优先测量模型、CPU预处理、解码及显示的耗时分布，再比较共享模型分支并发、硬件解码、CUDA预处理和联合检测；不预先承诺增加线程或减少一个模型就能达到目标。
