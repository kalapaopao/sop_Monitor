## 一、方案总览

### 1.1 一句话

**一台 NX 做推理与判定，通过 MQTT 把 SOP 结果推给 4 个工位，工位屏幕当场纠错；
数据沉淀到中央 TL3576，厂家用训练工具自助换型。**

### 1.2 分层结构

```
┌─────────────────────────────────────────────────────────┐
│ 采集层（已实现）                                          │
│   4 × GStreamer 硬解 H.265 → I420 → BGR                 │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ 推理层（已实现）                                          │
│   联合 OBB（4 类，batch 1/2/4，640×384）                  │
│   RTMW（133 点，固定 batch 4）                            │
│   → 每路 19 Hz（4 路）/ 25 Hz（1、2 路）                   │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ 输出层（待建）★ 当前最大缺口                              │
│   骨架流结构化输出（P1）                                  │
│   ├─ → MQTT → 工位屏幕（纠错）                            │
│   └─ → 落盘   → 训练数据集（换型）                         │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ 判定层（待建）                                            │
│   TCN 时序判定（窗口 64 帧 @ 采样率 → 约 2.5–6 秒）        │
└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│ 应用层（已具备 / 待接）                                    │
│   中央 TL3576：SQLite + React + 图片（已部署）             │
│   工位 TL3576：屏幕纠错（待接 MQTT）                       │
│   训练工具：厂家自助换型（待建）                            │
└─────────────────────────────────────────────────────────┘
```

### 1.3 已实现 vs 待建（诚实清单）

| 层 | 状态 | 证据 |
|---|---|---|
| 4 路硬解 + 推理 | ✅ **已实现** | 4 路 19.0 Hz，`ctest` 5/5 |

## 二、推理侧方案（已实现部分）

### 2.1 四路批量调度

**做法**：单线程串行 + 凑批，4 路每路最多取一帧，组成最多 4 帧的批。

```
4 × 最新帧槽（容量 1，忙时替换未开始任务）
        ↓ 公平轮询，最多等 5 ms 凑批
   原图只上传一次 → GPU 矩形预处理 640×384
        ↓
   按 det_batch 分块检测 → 解码 + 旋转 NMS
        ↓
   收集体检 ROI → 192×256
        ↓
   按 pose_batch 分块 → SimCC 解码
        ↓
   按 owner 与 frame_id 归还（末批不足时重复最后一项补齐）
```

**为什么这样设计**（都有实测依据）：

| 决策 | 依据 |
|---|---|
| 单 worker 而非多 context | `workerCount` 硬编码 1；Xavier 只有 6 SM，多 context 争抢更慢 |
| batch 4 而非 batch 1 | 吞吐 76.2 vs 55.2 fps（1.38 倍） |
| 矩形 640×384 而非方形 640×640 | 实测最优；方形多 33% 像素 |
| `rtmw_b4` 而非 `rtmw_b2`（4 路） | 19.13 vs 17.60 Hz |
| 队列容量 1 | 忙时替换，不堆积延迟 |

### 2.2 延迟语义（容易被误读）

- 4 路 `pose_age_p95 = 120 ms`，**只有 40 / 80 / 120 三档**，93% 滞后 2–3 帧。
- 这是**结构性**的：一组 4 帧需 52.5 ms，结果回来时画面已前进 1.3 帧，
  `eligible` 只允许 `frame->id <= f->id` 的结果，故至少落后一整组。
- **窗口 FPS ≠ 识别 Hz**，文档与报告一律用 `steady_job_hz` 口径。

### 2.3 精度

- **FP16 混合**，不是 int16（int16 不是 TensorRT 的精度类型）。
- 逐层精度**无法从引擎内省**（`kLAYER_NAMES_ONLY`），结论来自构建脚本。

## 三、输出层方案（P1，待建）

> **这是当前最重要的缺口**：没有结构化输出，后面采集、训练、纠错全部无法开始。

### 3.1 现状

现有能力是**离线校验**：`--sample-dir` 读固定 PNG，输出 `detections.csv` / `poses.csv` /
`samples.csv`。它不是流式的，也不带时间戳和工位信息。

### 3.2 目标：骨架帧记录（Frame Record）

每完成一次推理，产出一条记录：

```json
{
  "schema": "sop.frame.v1",
  "station_id": "A1",
  "lane": 0,
  "frame_id": 1042,
  "ts_ns": 1761091200123456789,
  "source_ts_ms": 41760.0,
  "latency_ms": 120.1,
  "persons": [
    {
      "bbox": [412.3, 208.1, 631.0, 902.7],
      "score": 0.94,
      "keypoints": [[512.4, 331.2, 0.91], "... 共 133 点 ..."]
    }
  ],
  "detections": [
    {"label": "screwdriver1", "score": 0.87, "obb": [512.0, 640.0, 88.0, 24.0, 1.57]}
  ]
}
```

**关键字段说明**：

| 字段 | 为什么必须有 |
|---|---|
| `station_id` | 下游要知道"这是哪个工位"，否则纠错无法路由（Q: 见需求 4.2） |
| `ts_ns` | 墙钟时间，用于与中央数据、工位事件对齐 |
| `source_ts_ms` | **视频内时间**，跨设备时钟漂移时仍可重建时序（TCN 真正需要的） |
| `latency_ms` | 结果年龄，用于判断这条数据是否可用于训练（太旧的可能配对错帧） |
| `persons[]` | 多人时保留全部；当前显示只取最高分一人，但**训练需要全部** |

### 3.3 两条消费路径

```
                     ┌→ MQTT（实时，只发精简版）
Frame Record ────────┤
                     └→ 落盘 JSONL（全量，供训练）
```

| 路径 | 内容 | 频率 | 用途 |
|---|---|---|---|
| MQTT | 判定结果（步骤/是否漏步），**几十字节** | 每次判定 | 工位屏幕纠错 |
| JSONL | 全量骨架 + 检测 | 每帧（4 路 = 76 条/秒） | 训练数据集 |

**MQTT 不发全量骨架**：全量数据走落盘，MQTT 只发结论。否则网络和工位屏幕都撑不住。

### 3.4 落盘性能评估（需实测）

4 路 × 19 Hz × 133 点 × 3 float ≈ **每秒约 1.4 MB 文本**（JSONL）。
按 8 小时计约 **40 GB/天**。

| 问题 | 方案 |
|---|---|
| 空间 | 中央 TL3576 有 106 GB 分区，可存 2–3 天；**需要采集期限 + 自动清理** |
| 写盘阻塞 | 走独立写线程 + 有界队列，队列满时**丢弃最旧**，绝不阻塞推理 |
| 二进制 vs 文本 | 先用 JSONL（可读、好调试）；量大再换二进制 |

**这一节的数据是估算，未实测**——P0 要做的第一件事就是验证真实落盘开销。

### 3.5 手部信息融合方案（OBB `hand` + RTMW 双手，待建）

> 动机是现场观察：`hand` 类的框在帧间会跳变，常有"只框出一只手、另一只手框不出来"的情况，
> 而 RTMW 往往两只手都能给出关键点。两条链路失效方式不同，才有互补的可能。
> **下面第 2 层要构造的"是否握住"，是后处理现算的几何量，不是 OBB 的结论。**

#### 3.5.1 先划清能力边界（容易误解的一点）

**OBB 的 `hand` 类只输出「一个旋转框 + 一个置信度」**，含义是"这一帧这个位置可能有一只手"。
它**不输出手的姿态**（手指朝向、手腕角度都没有），
**也不知道手里有没有东西、是不是握住了螺丝批**。

依据：

| 事实 | 位置 |
|---|---|
| 类别只有 `screwdriver1 / screwdriver2 / hand / person`，手与工具之间无关联输出 | `src/models/joint_detector.hpp:30` |
| 旋转 NMS 只在同类之间做 IoU 抑制（0.55），不产生跨类关系 | `src/models/joint_detector.hpp:48` |
| 离线特征里 `hand_box_*` 只有 8 个字段，**没有角度** | `prepare_robust_features.py:61` |
| `angle_policy` 明确写 "hand has no angle" | `prepare_robust_features.py:107` |
| `hand_box_*` 与 RTMW 手部点**完全不相连**，是两段独立特征块 | `prepare_robust_features.py:75-78` |

所以 3.5.4 要构造的"手是否握着螺丝批"，**必须在后处理里现算再交给 TCN 学**。
实施时不能写出"模型告诉我他握住了"这种不存在的字段。

#### 3.5.2 两条链路为什么能互补

| 链路 | 给什么 | 典型失效 | 失效时表现 |
|---|---|---|---|
| OBB `hand` | 旋转框 + 置信度，**不区分左右手** | 遮挡、手只露一部分、两手挨得近 | 漏检一只手，或两只手只出一个框 |
| RTMW 手部点 | 左右手各 21 点（索引 91 / 112 起）+ 每点分数 | 手腕被躯干挡住、手出画、快速运动 | 分数掉下去，或坐标贴边 |
| RTMW 上身点 | 肩 5/6、肘 7/8、腕 9/10、髋 11/12 | 侧身、背对镜头 | 位置漂移，但通常仍有值 |

OBB 靠外观纹理，RTMW 靠人体结构先验——**失效不同源**才有互补价值。
若实测发现两者总是一起失效，这套设计就没有意义，见 3.5.7 的分叉。

#### 3.5.3 第 1 层：手框 ↔ 手腕的空间关联

**目的**：把匿名的 `hand` 框绑定到左/右手，并给下游一个"这条链路可不可信"的标志。

对每个 `hand` 框，取框中心 `c_box` 与长边 `s = max(w,h)`，与 RTMW 左右腕点
（索引 9 / 10）分别算归一化距离 `d_side = |c_box - p_wrist_side| / s`，
按 `d_side` 做贪心一对一配对（一个框只认一只手）：

| 状态 | 条件 | 含义 | 下游怎么用 |
|---|---|---|---|
| **双确认** | 有框且该侧腕点分数 ≥ 阈值 | 两条链路都认为这只手在 | 最可信 |
| **OBB 独占** | 有框，该侧腕点分数低 | 骨架漏了手 | 位置可用，**姿态不可用** |
| **骨架独占** | 无框，该侧腕点分数正常 | 框漏了，骨架还在 | 位置可用，**少了独立旁证** |

输出字段（并入 3.2 的 Frame Record，每侧一组）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `hand_L_box_conf` / `hand_R_box_conf` | float | 关联到该侧手框的置信度，无框为 0 |
| `hand_L_kpt_score` / `hand_R_kpt_score` | float | RTMW 该侧腕点分数，未检出为 0 |
| `hand_L_agree` / `hand_R_agree` | 0/1/2 | 0=都没、1=单边、2=双确认 |
| `hand_L_occluded` / `hand_R_occluded` | 0/1 | 见 3.5.5 |

**硬原则**：三层都**不做坐标插值、不做外推、不凭空补点**。
缺失用标志位表达，让 TCN 自己学"缺的时候意味着什么"。
补出来的坐标会污染训练数据，且验收时无法与真实观测区分。

#### 3.5.4 第 2 层：手 ↔ 螺丝批的几何关联

给 TCN 两个**可计算**的几何量（不是模型的判断）：

| 指标 | 定义 | 范围 |
|---|---|---|
| `iou_L_sd1` | `hand` 框与 `screwdriver1` 框的旋转框 IoU（复用 `polygonIou`，`src/core/main.cpp:357`） | 0–1 |
| `dist_L_sd1` | `|c_hand - c_sd1| / max(w_hand, h_hand)` | ≥0，越小越近 |

对 `L/R × screwdriver1/2` 四个组合各算一遍，得 8 个连续特征，
再各派生二值 `hand_L_holds_sd1 = (iou >= θ_iou) && (dist <= θ_dist)`。

**阈值 `θ` 必须由数据定**：先在采集数据上画 `iou` / `dist` 分布，
取能分开"接触 / 未接触"的位置（3.5.7 第 3 项）。**当前无阈值，待定。**

**为什么不做成"模型告诉我握住了"**：OBB 没有这个输出（3.5.1）；
硬写规则又等于把工艺知识编码进程序，违反 D2。正确形态是
**程序只算几何，握持语义由 TCN 从数据里学**。

⚠️ **与现有 F1 的关系是推断，不是已验证结论。**
183 维特征里已有 `hand_box_cx/cy/width/height` 与 `screwdriver*_cx/cy/...`，
网络理论上能自己学到同样的关系；显式加 `iou`/`dist` 是否有增益**未做消融，未知**。
且 `pilot_08_clean` 仅少 6 个工程字段 F1 就从 0.6620 掉到 0.5787（§4.1），
说明该模型对特征维度敏感——**加特征不一定涨点，必须先消融再决定是否常开**。

#### 3.5.5 第 3 层：单侧缺失的时序补全（只补"存在"，不补坐标）

```
若 上一帧 hand_L_agree >= 1 且 本帧 hand_L_agree == 0 且 本帧该侧腕点分数正常：
    hand_L_occluded = 1      # 标记疑似遮挡/漏检，agree 仍为 0，坐标仍为空
连续 N 帧仍为 0 → occluded = 0，视为确实离手/出画
```

`N` 按采样率折算（19 Hz 下 3 帧 ≈ 160 ms，5 帧 ≈ 260 ms），**初值建议 3，需实测调**。
另可存 `*_last_seen_ms` 供 TCN 参考"多久没看到"，但**不冒充本帧坐标**。

#### 3.5.6 第 4 层：裁剪重跑手部模型（**不推荐**）

思路是用 OBB 手框裁剪后单独送手部关键点模型。不推荐的理由：

1. 每路每帧多一次前向，4 路 19 Hz 下直接吃掉 OBB 与 RTMW 之外的全部余量；
2. 引入第三个模型与第三份引擎，部署体积与插件依赖都增加；
3. `pilot_08_hand_stride1`（只留手部关键点，F1 0.4821）说明**手部单独用不如配合人体**（§4.1），
   再叠一个手部模型未必解决"不稳定"这个真问题。

除非 3.5.7 显示 RTMW 手部在关键场景系统性失效且几何无法补救，才重新评估。

#### 3.5.7 先做三个离线测量（不改进推理，只读现有 CSV）

在写任何融合代码之前，用 `--validation-dir` 已导出的 `detections.csv` + `poses.csv`
（`src/pipeline/batch_runner.hpp:62`）先量：

| # | 测什么 | 怎么算 | 用来决定 |
|---|---|---|---|
| 1 | **每帧 `hand` 框数量分布** | 0 / 1 / 2 / ≥3 帧的占比 | 缺失多不多，值不值得做融合 |
| 2 | **OBB 只出一个手时，RTMW 另一只手的分数** | 筛出单框帧，看未配对侧的腕点及 21 点均分 | **决定性**：分数正常 → 真互补；分数也低 → 不互补，改走"标记 + 时序平滑" |
| 3 | **手框 ↔ 螺丝批框的 IoU / 中心距分布** | 分"握持 / 未握持"两组看分布 | 定 3.5.4 的阈值；分布不可分则这组几何量无用 |

**分叉结论**：

- 第 2 项 RTMW 仍正常 → 互补成立，按 3.5.3–3.5.5 实施；
- 第 2 项 RTMW 同时掉分 → **融合无收益**，接受缺失，在 TCN 侧用 `occluded` + 时序模型兜住，
  **不要为了"看起来完整"去补点**；
- 第 3 项分布不可分 → 放弃 `holds_*` 二值，只留连续 `iou` / `dist`。

三项都只吃 CPU 和现有 CSV，**不占 NX 推理资源，不影响 4 路 19 Hz**。

#### 3.5.8 顺带修正：选人打分把手腕算进去了

```cpp
// src/pipeline/batch_runner.hpp:47（同样逻辑另见 pipeline.hpp:156、core/main.cpp:513、dual_probe.cpp:284）
const float score = std::accumulate(pose.scores.begin()+5, pose.scores.begin()+11, 0.f) / 6.f;
```

`5..10` = 双肩、双肘、**双腕**。用它挑"这一路保留哪个人"的副作用是
**手部越清楚的人越容易被选中**。单人工位通常无害，但画面里出现第二个人时，
"手部可见性好"会压过"人更靠近工位"，与"以人体骨架为核心"的目标不一致。

**建议改为躯干四点 `5, 6, 11, 12`**（双肩 + 双髋）——`main.cpp:480` 的骨架连线已在用
`{5,11}` `{6,12}` `{11,12}`，髋点存在。这样选人只依赖躯干稳定性。

⚠️ 这会改变"多人场景保留谁"的**可观测行为**，必须与 3.5.7 的基线对比同批做，
**不能静默修改**；且四个入口是同一份逻辑，改动需同步四处。

#### 3.5.9 开销

三层融合全是后处理：几次浮点运算 + 最多 4 次 `polygonIou`（4 点多边形求交）。
相对一组 4 帧 **52.52 ms** 可忽略——整条后处理链目前只占 **2.3%**（需求文档第六节），
融合加进去仍在同一量级，**不改变 4 路 19 Hz 的结论**。
真正的代价是 **Frame Record 变宽**（每侧多 4 + 8 个字段），而这本就在 P1 范围内。

## 四、判定层方案（TCN，待建）

### 4.1 现有实验（`project/tcn_usescrewdriver-hand/`）

| 项 | 值 |
|---|---|
| 网络 | `pytorch-tcn`，3 × 64 通道残差块，核 5，**causal=True** |
| 窗口 | 64 帧（默认） |
| 标签 | BORIS 人工标注，二分类（是否正在使用螺丝批） |
| 数据 | 单个视频 08，按动作片段切分（前 4 段训练 / 第 5 验证 / 第 6 测试） |

**四组实验的实际结果**（`artifacts/*/report.json`）：

| 实验 | 特征维度 | 测试 F1 | 说明 |
|---|---:|---:|---|
| `pilot_08_segmented` | 183 | **0.6620** | **当前最好**，完整特征 + 按片段切分 |
| `pilot_08_clean` | 177 | 0.5787 | 去掉推理耗时与 OBB 角度字段后下降 |
| `pilot_08_hand_stride1` | 243 | 0.4821 | 移除人体骨架、只留手部（控制组） |
| `pilot_08_hand_stride4` | 243 | 0.3506 | 手部再降频到每 4 帧 |

**已验证的结论**：
- **人体骨架是必要线索**：只保留手部关键点，F1 从 0.662 掉到 0.482。
- 手部降频会进一步恶化（0.482 → 0.351），**不能靠降低 RTMW 频率省算力**。
- 去掉"推理耗时/OBB 角度"这类工程字段也会掉点（0.662 → 0.579），说明特征选择敏感。

**尚未验证**：跨视频泛化（只测了单个视频）。

### 4.2 从"二分类"到"多步骤"的差距

现有实验只判"是否在用螺丝批"，**不是 SOP 步骤识别**。要变成多步骤，需要：

| 差距 | 说明 |
|---|---|
| 标签体系 | 从二分类变成"第 N 步"多分类（或每步一个二分类） |
| 数据量 | 需要覆盖所有目标步骤、多个工人、多个产品 |
| 步骤划分 | **由数据里找高频重复动作**（需求 D1），不是事先人工定义 |
| 状态处理 | 步骤间的转移由模型学，或写在配置里，**不能硬编码进源码**（D2） |

### 4.3 部署形态（待定）

| 方案 | 优点 | 缺点 | 状态 |
|---|---|---|---|
| **PyTorch + torch2trt** | 训练/推理同一套代码 | 转 TRT 有兼容风险 | 待评估 |
| **导 ONNX → TRT** | 复用现有 C++ 推理框架 | 需处理动态窗口 | **倾向此方案** |
| **纯 PyTorch（CPU）** | 最简单 | 4 路 × 19 Hz 可能跟不上 | 需实测 |

TCN 计算量很小（3 × 64 通道、核 5、64 帧窗口），估算 1–3 ms/次；
4 路 × 19 Hz × 1 ms ≈ 7.6% 单核占用。**但这是估算，未实测（见需求 Q1）。**

## 五、通讯方案（MQTT，待建）

### 5.1 拓扑（沿用现有设计）

```
NX 本地 Broker（已装 mosquitto，active）
  ├─ 工位 1 TL3576 ←→ 订阅纠错 / 上报触发
  ├─ 工位 2 TL3576
  ├─ 工位 3 TL3576
  └─ 工位 4 TL3576

中央 TL3576 Broker（192.168.1.20:1883）
  └─ NX 连接：设备上线 / 模型管理（可选，非实时链路）
```

**两条链路分离**（`当前系统架构.md` 已定）：
- 生产实时走 NX 本地 Broker，**中央断网不影响现场**
- 管理通道走中央 Broker，只传模型管理小消息

### 5.2 Topic 设计（建议）

| Topic | 方向 | 载荷 |
|---|---|---|
| `sop/{station}/trigger` | 工位 → NX | `{"trigger": true}` |
| `sop/{station}/heartbeat` | NX → 工位 | `{"alive": true, "fps": 19.0}` |
| `sop/{station}/judge` | NX → 工位 | `{"step": 3, "expected": 4, "alert": "missing_step", "ts": ...}` |
| `sop/{station}/snapshot_request` | NX → 工位 | `{"reason": "alert"}` |

**只发结论，不发骨架**（见 3.3）。

### 5.3 可靠性

| 场景 | 处理 |
|---|---|
| 工位离线 | MQTT 保留消息 + 工位重连后拉最新状态 |
| NX 重启 | 重新发布 `system/ready` |
| 消息丢失 | 判定结果用 QoS 1；心跳用 QoS 0 |
