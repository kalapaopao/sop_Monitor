# 05 · 踩坑与注意事项

> 读者：接手代码的开发者。**每条都是实际踩过、有证据的**，不是猜测。

## 1. ⛔ 最贵的坑：letterbox 留边没回代 → 骨架整体偏移

**现象**：网页上骨架大致在手附近，但明显"漂"，最多偏 57 px；人物框越偏离 3:4，偏得越多。

**根因**：`run_local_pose.py` 的 `crop_person()` 把人体框按比例缩放后**居中**贴在
192×256 的画布上（四周留黑边 `left` / `top`），而旧版 `decode()` 把整张 192×256
当成人体框来反算，**漏扣了 `left` / `top`**。

实测偏差（旧数据）：

| 时间 | 人体框 | 留边 | 关键点偏差 |
|---|---|---|---|
| 6.0 s | 760×944 | top 8.8 | ±9 px |
| 12.4 s | 994×1080 | top 23.7 | −23 px |
| 20.0 s | 780×791 | top 30.6 | +15 px |
| **45.0 s** | 956×1021 | top 25.4 | **−57 px** |
| 75.0 s | 675×957 | left 5.8 | +11 px（水平也错） |

**正确公式**（现已实现）：

```python
x = meta['x0'] + (cx - meta['left']) / meta['scale']
y = meta['y0'] + (cy - meta['top'])  / meta['scale']
```

**规矩**：`crop_person()` 与 `decode()` 必须**成对修改**。任何改动后重跑
`run_local_pose.py` **和** `render_pose_video.py`，否则视频里的骨架与底部片段条不一致。

## 2. 模型在遮挡时会"编"一只手出来

RTMW 是单帧回归，手被身体/工件挡住时仍会输出 21 点，常见的两种假象：

- 21 点几乎重合（挤成一个"点团"）；
- 整只手的点被外推到画面边缘（贴在边框上）。

旧数据里 12.4 s 那只手就被外推到画面最右侧。现由 `keep_hand()` 过滤：

```python
score_thr = 0.18, min_extent = 30.0, border = 8.0
# 有效点 < 4 → 丢弃；点集包围盒最大边 < 30 px → 丢弃；任一点距画面边 < 8 px → 丢弃
```

`min_extent` / `border` 是**经验值**，换分辨率或换机位需重调。
过滤后有效帧变少是**预期行为**（左手 517→459），不要当成 bug 去"修回去"。

### 2.1 补一层"手掌几何一致性"过滤（2026-11-14 新增）

`min_extent` / `border` 两个条件**拦不住"撒成星形"的假检测**：实测 12 秒附近，
21 个点散布在 250 px 范围里、连不成一只手，但仍通过了两项检查，画出来就是一堆乱线。

判据：**掌骨长度一致性**。用腕点(0)到 5 个掌指关节(1/5/9/13/17)的距离，
正常手这 5 段长度接近；撒成星形时 max/min 会明显变大。

实测分布（953 个手样本）：`p50=2.84, p75=3.46, p90=4.99, p95=6.82, p99=10.55, max 巨大`。
阈值取 **5.0**（`--max-palm-ratio`），12 秒那几帧（5.01 / 6.76）被剔除，
而 45 秒、6 秒这些肉眼验证过的正常帧（2.38~3.48）全部保留。

代价：右手有效帧 502 → 413（-18%），左手 459 → 452。
**这是刻意用覆盖率换观感**，底部进度条会变短但更可信；不想要就传 `--max-palm-ratio 0`。

### 2.2 显示框和 ROI 框必须用不同的外扩量

同一个框同时用于"画面上画"和"裁 ROI"会两边都不对：

| 用途 | 外扩 | 原因 |
|---|---|---|
| 画面显示框 | `--box-pad 0.10` | 大了就像画了个大框套住半个桌面 |
| ROI 裁图 | `--pad 0.40` | 小了会把手里拿的工具/工件裁掉 |

首版两者都用了 0.4，结果画面上手框是手的 2 倍大，看起来"框没框住手"。
第二版把显示框调到 0.10，又变成**比手还小**（实测框/手 = 0.92，69% 的框套不住手）——
因为 MAD 剔离群点砍掉了指尖，基准边长只剩完整跨度的 77%，再乘 1.2 还是不够。

**最终做法（2026-11-14）**：显示框**不剔离群点**（`robust=False`）+ `box_pad=0.25`，
实测框/手 = **1.50**，框中位 149 px、手跨度 99 px，0% 的框小于手。

## 2.4 ⛔ 手框不能当"模型看的范围"用（2026-11-14 修正）

**现象**：使用者反馈"手框很多时候只框住手，或者框住半个工具、1/3 个工件"。

**根因**：手框是 21 个**手部关键点**的外接框，关键点全部落在手表面，
所以框内**永远不包含工具/工件**；工具伸出框多少，只由那个固定百分比外扩决定。
而工具与手的比例差别极大（螺丝刀可伸出去 2~3 倍手长，小螺丝完全在手里），
**任何固定百分比都不可能同时适配** —— 这是原理问题，不是调参问题。

**修正：把"显示"和"模型输入"分成两个框**

| 框 | 用途 | 算法 | 实测 |
|---|---|---|---|
| 手框（实线） | 给人看"手在哪" | 关键点外接 + 32% 外扩，不剔离群点 | 中位 153~170 px |
| **上下文 ROI（虚线）** | **模型实际裁图的输入** | `max(0.35×人体框高, 2.2×平滑手部尺度)`，夹在 180~700 px | **中位 342~344 px（画面宽 17.8%）** |

关键设计：**ROI 尺度以"人体框高度"为主**（`--person-k 0.35`），因为人体尺度比手部稳定得多。

实测稳定性对比（ROI 边长相邻帧跳变）：

| 尺度来源 | 中位跳变 | >100 px 占比 |
|---|---|---|
| 瞬时手部外接框 | 12 px | 3.8% |
| **人体高度 + 时间中值平滑** | **2 px** | **0%** |

手部关键点外接框在 59~648 px 之间跳（10 倍），直接当 ROI 边长会让同一只手被裁成
完全不同的比例，CNN 特征不可比。所以 `smooth_scale()` 做了 ±0.8 s 的时间中值平滑，
且只用它作下限（`--hand-k 2.2`）。

校验方法：带框视频与原视频同帧 `cv2.absdiff`，差异区域应等于
「手框 ∪ ROI ∪ 文字标签」的范围。实测 t=45 差异 bbox `(884,547,1279,995)`，
四框并集 `(889,573,1275,998)`，上边界差 26 px 来自框上方的文字标签。

## 2.5 骨架和框必须一起烧进视频，不能一半烧一半画

曾经的做法是"骨架烧进视频、手框用网页 canvas 画"，用户在页面上看出不对：
骨架 24.7 fps 平滑，手框只有 5 Hz 且**没有插值**，每 0.2 秒跳一次，观感明显割裂。

现在统一：`render_pose_video.py --boxes` 把**手框（实线）和上下文 ROI（虚线）**都画进画面，
`App.vue` 里**没有 canvas、没有 drawBoxes**（已删除）。代价是改框要重渲染约 2 分钟。

## 2.6 ⛔ 框不插值 → 播放时"一卡一卡"（2026-11-14 修正）

**现象**：使用者反馈"矩形框和虚线框一卡一卡的"。

**先澄清**：**没有抽帧**。源视频与输出视频都是满帧 **2964 帧 / 24.702 fps**。

**根因是两层**：

1. **框没有插值**。`hand_at()` 对骨架做了线性插值，但 `box_at()` 当年写的是
   "取最近帧不插值"，理由是"框是离散判定"——这个理由只对**有没有框**成立，
   对**框在哪、多大**不成立。姿态 5 Hz、视频 24.7 fps，约 5 个视频帧共用同一个姿态样本，
   所以框每 0.2 秒才动一次。
2. **采样率偏低**。即使插值，5 Hz 的插值仍是折线，快速动作时能看出折角。

**修正**：

| 项 | 改前 | 改后 |
|---|---|---|
| `box_at()` | 取最近帧，不插值 | 两端都有效则**按时间线性插值**坐标；只有一端有效则用最近的（限 0.35 s） |
| 姿态采样率 | 5 Hz（600 帧） | **10 Hz（1200 帧）**，`--rate` 默认值已改 |
| ROI 尺度平滑 | 时间**中值** | 时间**高斯加权均值** |

为什么中值要换成高斯均值：中值是"分段常数"，相邻采样点经常取到完全一样的值，
插值后仍是一段段静止（实测零位移帧占 26~32%）。高斯均值每个采样点都略有变化，
配合插值就是连续的。

**实测（同一段 20~40 s，统计相邻视频帧的框位移）**：

| 版本 | 手框零位移帧占比 | ROI 零位移帧占比 |
|---|---|---|
| 5 Hz + 不插值 | **84%** | **87%** |
| 5 Hz + 插值 | 22% | 37% |
| 10 Hz + 插值 + 高斯平滑 | **15~16%** | **20~21%** |

成片复核：ROI 区域相邻帧平均差异中位 0.206，近零（<0.05）帧占比 **0%**（改前约 80%）。

## 2.7 ⛔ `HAND_MERGE_GAP` 曾是死代码，时间轴碎成几十条

**现象**：底部"左手/右手识别片段"有 61 条和 82 条，密密麻麻。

**根因**：`buildSegments()` 里一旦遇到无效帧就先 `segs.push(cur); cur = null`，
片段已经收尾了；于是后面那句 `t0 - cur[1] <= HAND_MERGE_GAP` 的合并分支**永远不会执行**
——`HAND_MERGE_GAP` 改成多少都没用（实测 gap 取 0.35/0.6/1.0，片段数都是 61/82）。

**修正**：遇到无效帧时**不立刻收尾**，只 `continue`，把"是否断开"交给下一个有效帧决定。
尾段在循环结束后补收。

**效果（10 Hz / gap = 0.6）**：

| | 片段数 | 覆盖时长 |
|---|---|---|
| 修前 | 左手 61 / 右手 82 | 89 s / 83 s |
| **修后** | **左手 17 / 右手 17** | **97 s / 94 s** |

顺带覆盖率也上去了（74%/69% → 81%/78%），因为短时遮挡不再被算成"断开"。

**现象**：`http://localhost:5173/` 能开，`http://127.0.0.1:5173/` 连接被拒；
`Get-NetTCPConnection` 看到监听地址是 `::1`。

**处理**：`web/vite.config.js` 已写死

```js
server: { host: '127.0.0.1', port: 5173, strictPort: true }
```

`strictPort: true` 意味着端口被占时**直接退出**，不会自动换端口——这是刻意的，
避免"起了两个服务、连到旧的那个"。旧 dev server 没退时先杀进程。

## 4. 为什么不再用 canvas 叠加骨架

旧方案 `<canvas>` 绝对定位盖在 `<video>` 上，踩过这些坑：

- 需要自己处理 DPR（否则高分屏模糊）、`ResizeObserver`（否则缩放后错位）；
- 只有 `timeupdate`（约 4 Hz）触发重绘，骨架跟不上画面，看起来"抖"；
- 距最近关键点帧超过 0.6 s 时若不判空，会画出"幽灵骨架"（该时段明明没识别到）。

现方案：离线烧录 → 没有时间同步问题。**代价**是换参数必须重渲染（约 2 分钟）。
`render_pose_video.py` 里对相邻两帧做线性插值（5 Hz → 24.7 fps），保证连续。

## 5. 两条链路的时间基准不同

`ablation_14_*.json` **只覆盖 0–30 s**，`local_pose_2min.json` 覆盖 0–119.99 s。
页面上「工序」轨道因此是"30 s 内容铺满 120 s 轨道"的占位显示，已加小字说明。
改 UI 时不要把两条轨道当成同一坐标尺度去对齐。

## 6. 孤儿文件 `src/style.css` 是个陷阱

根目录 `src/style.css` 里正是 `.video-wrap{position:relative}` 和 `.pose-overlay{...}`
——让人以为"CSS 写了"，但 Vite 只加载 `web/src/style.css`，这个文件永远不会生效。
排查这类问题务必确认**文件是否真被引用**（`grep -r "style.css" web/`）。

## 7. `requirements.txt` 与代码不一致

文件里只有 `openai>=1.0.0`、`opencv-python>=4.8.0`，
但 `run_local_pose.py` 实际还需要 `onnxruntime`、`ultralytics`、`numpy`。
**新建环境必装**，否则 `ImportError: onnxruntime`。

## 8. `response` 字段是"字符串里的 JSON"

```python
json.loads(item['response'])   # 需要二次解析
```

前端必须 `try/catch`，否则一条脏数据会让整页白屏（已加兜底）。

## 9. 三组消融的输出语言不一致

A 组中文、B/C 组英文（同一提示词、temperature 0.1）。属模型抖动，不是代码 bug。
要统一需在提示词里强制语言，或做后处理映射。

## 10. 视频素材本身有坑

| 文件 | 问题 |
|---|---|
| `vedio/v2_5m_7m.mp4` | 编码部分浏览器解不了，历史页面专门做了 fallback |
| `vedio/v2_5m_7m_h264.mp4` | 帧率是 `12351/500 ≈ 24.702`，**不是整数**；按 25 fps 算时间会累积误差 |
| `web/public/video/*.mp4` | 三个共 318 MB，页面**只引用** `v2_5m_7m_pose.mp4` |

`render_pose_video.py` 用的是 `cap.get(CAP_PROP_FPS)`，与 `run_local_pose.py` 一致，
所以两者时间戳对齐；**不要**自己写死 25 fps。

## 11. 用无头浏览器截图验证会看到"旧帧"

`msedge --headless --virtual-time-budget=... --screenshot` 常常截到 **seek 之前的画面**，
曾导致误判"骨架错位"。要验证请走 CDP：

```js
video.currentTime = 45
await new Promise(r => video.addEventListener('seeked', r, { once: true }))
await new Promise(r => setTimeout(r, 700))
// 然后用 Page.captureScreenshot
```

## 12. Windows 下的编码问题

## 15. ⛔ `.venv` 是"借来的"环境，动了会影响另一个项目

实测：

```text
sys.prefix = ...\sop_offline_teacher\.venv
onnxruntime -> E:\study\X-AnyLabeling-main\x-anylabeling-env\Lib\site-packages\...
ultralytics -> 同上
cv2 / numpy / torch -> 同上
.venv\Lib\site-packages 自己的包数 = 16
```

`.venv\pyvenv.cfg`：

```ini
home = E:\study\X-AnyLabeling-main\x-anylabeling-env
include-system-site-packages = true
```

**后果**：

- 在这台机器上 `pip install` / `pip uninstall` 会**同时改动 X-AnyLabeling 那个工程**的环境；
- 把 `.venv` 拷给别人**用不了**（依赖不在里面）；
- `pip list` 看起来"什么都有"，容易误判项目环境完整。

**规范做法**：

```powershell
python -m venv .venv          # 不要加 --system-site-packages
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

**只有确认要连带升级 X-AnyLabeling 环境时**，才在当前 `.venv` 里装包。
