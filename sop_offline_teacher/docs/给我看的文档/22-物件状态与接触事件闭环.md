## 1. 关键实测一：现有固定 ROI 不能直接当状态框用

现有 3 个 `focus` 区域是为「注意力引导」画的，不是为「物件状态观测」画的。

`scripts/probe_hand_zones.py`（全片 10495 个有效腕点）给出两个数：

| 区域 | 框内腕点占比 | 框面积占比 | 倍数（越高越是真作业区） |
|---|---|---|---|
| 桌面区域 `rmwhj0yaa` | 89.2% | 25.7% | 3.47 |
| 放料区域 `rmwhj1904` | 19.2% | 4.8% | 3.98 |
| **取料区域 `rmwhj1lpv`** | 10.1% | 6.1% | **1.64**（最低） |

`scripts/station_state_obs.py` 的逐帧统计更直接：**`取料区域` 矩形平均 72.5% 的面积被工人框覆盖**。
它盖在人身上，不在料盘上。在这样的框里算"区域外观变化"，测到的是人的运动。

→ **结论：不能把 focus 框改个 type 就当状态框。必须重新定框。**

## 2. 关键实测二：从手腕停留反推工位布局（数据驱动定框）

`probe_hand_zones.py` 的手腕热力图显示：手的活动集中在画面 x≈0.48–0.78、y≈0.22–0.62；
顶部 y<0.2 几乎没有腕点。停留中心（速度<0.2/s 持续≥3s，共 59 段）收敛得非常干净：

| 位置 | 中心 | 出现情形 |
|---|---|---|
| 左手作业位 | (0.51, 0.48) | 多个周期反复出现 |
| 右手作业位 | (0.54, 0.31) | 与左手同时出现，右手在左手上方 |
| 取料/供料位 | (0.70, 0.26) | 46.9–60.9s 右手停留 14.0s |
| 另一作业位 | (0.60, 0.68) | 43.5–60.9s 左手停留 17.4s |

据此把 `configs/stations.json` 的 state 区域**按实测坐标重画**（原 focus 三个框坐标一字未改）：

## 3. 关键实测三（负面结论）：本机位下"物件有无"读不出来

`station_state_obs.py` 在收紧框上跑全片 5992 tick（背景 = 整段 600 抽样帧的逐像素中位数）：

| 区域 | fg 中位 | **安静 fg 中位**（手不在区内时） | 手在内比例 | 人框覆盖 |
|---|---|---|---|---|
| state_asm | 0.386 | 0.277 | 0.595 | 0.675 |
| state_feed | 0.723 | 0.728 | 0.103 | 0.864 |
| state_out | 0.513 | 0.478 | 0.319 | 0.824 |

**三个区都没有出现"有件/无件"的双峰分布，安静读数也不比整体低多少。**
`probe_object_regions.py` 排除了人框后按粗网格统计，也只有顶部 x 0.38–0.44、y 0–0.22
（obj_activity 0.30–0.34，cover 0.005–0.13）和左下角 x 0–0.13、y 0.56–0.89 这两块是
"物件在变且人不挡"，但都不在装配作业面上。

**物理解释**：摄像机俯视工位，作业面长期被手臂覆盖，"件"始终在手臂下方。
这不是算法调参能解决的，是机位决定的。

→ **结论：本机位不能靠背景差分得到干净的物件状态序列。这条路本轮判为不可用，并留下量化依据。**
（换侧向机位、或在工装上加固定标尺/传感器，才可能成立。）

## 4. 能工作的通道：双手稳定构型（纯骨架，与手法无关）

改成用"这件事在物理上发生了"来定事件（`scripts/build_behavior_events.py`）：

| 事件 | 定义 | 全片数量 |
|---|---|---|
| dwell | 单侧手腕 0.5s 窗口位移速度 < 0.08/s，持续 ≥2s | 120 |
| **two_stable** | 左右手同时 dwell，且两手相对构型波动 ≤0.05 | 44 |
| reach | 手腕进入状态框并停留 ≥0.4s | 81 |
| away | 双手都不在作业框内 ≥1.5s | 36 |

紧固的物理形态是「稳定施力 + 小范围换位」的交替：单次稳定只有 2–6s，
按间隔 ≤8s 合并后得到 **7 段紧固候选**（GT 6 段）。

## 5. 与 GT 对齐（全片 606s / 37 段有效 GT，剔除 nested_short）

`scripts/eval_events_vs_gt.py`，容差 ±2s：

| 指标 | 结果 |
|---|---|
| **GT 步骤时长被非空闲候选覆盖** | **96.2%** |
| 紧固（S5）命中 | **6/6**，IoU 0.25–0.76（中位 0.52），段数 7 vs 6 |
| S3 组装上盖 | 4/7 命中 |
| S4 装密封塞 | 1/7 命中 |
| S1 取镜座 / S2 取上盖 / S6 系扎带 | **0/9、0/7、0/1** |
| 边界召回（±2s） | 40.5% |
| 边界精确（±2s） | 54.0% |
| GT 边界到最近候选的中位误差 | 4.60s |

**读法**：本地事件把"什么时候在干活"几乎全部抓住了（96.2%），
长时间动作（紧固）的边界也落在正确位置；
但**短动作完全分不出来**——这正是需要交给 Qwen 的那一半。

### 5.1 一个意外的有用发现

GT 的「系上镜座扎带」在 329.6–341.6s，**落在两个作业区之外**。
本地规则把它切成了独立段 329.8–341.5（时间几乎完全吻合），但归到了 idle ——
因为那一分钟里手部关键点缺失，速度算不出来。

→ **S6 不是"多一种动作"，而是"动作发生在别的位置"。**
把它并入 S5 会丢掉这个结构信息；正确做法是新增一个"扎带位"状态框。

## 6. 与 Codex 方案的三处差异（必须知道）

| # | Codex 的方案 | 实测后改成 | 依据 |
|---|---|---|---|
| 1 | 把固定区域从 focus 扩展为 state | **焦点框不动；另按手腕停留实测重画 3 个 state 框** | 原 `取料区域` 72.5% 被人框覆盖（§1） |
| 2 | 用物件状态变化产生候选步骤 | **改为用事件语法（停留/双手稳定/往返）产生候选** | 物件状态通道在本机位不可用（§3） |

第 2 条仍然满足"以物理事件为主判据"的本意，但**必须承认**：本轮的主判据是"人的双手在做什么样的稳定构型"，
而不是"物件状态变了"。这两者的抗手法能力不同——前者仍部分依赖姿态，后者才是真正与手法无关的。
在拿到侧向机位之前，前者是能做到的最好版本。

## 9. 已知缺陷与下一步（按证据强度排序）

## 10. 更正（同日）：§5 的"96.2% 覆盖"是自我美化的指标，主信号已换回帧级模型

### 10.1 我错在哪

§5 报的「GT 步骤时长被非空闲候选覆盖 96.2%」，只要把大片时间刷成 `ASSEMBLE` 就能拿高分，
**它不反映"工序切得对不对"**。真实情况是：120 秒窗口里人工标了 12 个步骤，
事件法只命中 2 个（16.7%），其余全被压成一个大 `S3` 块，边界中位误差 5.20 秒。
`S6` 系扎带整段被吞成 idle。**这个结果不能交付。**

根因不是参数没调好，是**路线错**：项目里本来就有帧级 88.62% 的分类器
（`api_runs/pred_mlp_hmm.json`，7 周期留一、无泄漏），我却绕开它，
用「手腕停留/往返」启发式从零重建分段，把分类能力整个丢掉了。

### 10.2 换回帧级模型 + 只改后处理，同口径对比

新增 `scripts/build_segments_from_pred.py`：帧级预测 → 0.1s 栅格补齐 → 迟滞
→ **类别自适应最短段**（用 `configs/sop_steps.json` 的 `expected_sec`，
不再用统一阈值，否则 0.2–2.0 秒的 S2 必然被抹掉）→ expected_sec 越界剔除 → 合并。
