## 二、裁决：两套词表到底用哪套？

### 2.1 两套表的本质区别

| | 参考视频 10 条 | 我们 6 条 |
|---|---|---|
| 来源 | 从 reference2.mp4 OCR 出来的**成品表现** | 从**你自己的 BORIS 标注**归纳的工序 |
| 描述粒度 | 一条里含多个动作（"取得黑色壳片**并与**银灰件靠合"） | 一条一个动作 |
| 兜底 | 有两条专门的异常/循环类（"流程外""循环外停留与准备"） | idle/unknown（简单） |
| 对应场景 | 银灰带筋件 + 黑色壳片 + 带线壳体（**另一个产品**） | 镜座组件 + 上盖 + 密封塞（**你的产品**） |
| 有无 GT | ❌ 无标注可对 | ✅ 38 段人工标注，可算准确率 |

### 2.2 裁决

**保留我们自己的 6 条作为主线，不换成参考视频的 10 条。理由：**

1. **产品不同**。参考视频装配的是"银灰带筋件/带线壳体"，你的 GT 标的是"镜座组件/上盖/密封塞"。
   换了词表 = 你的 38 段 GT 全部作废，一切准确率评测失去基准。
2. **参考视频的 10 条无 GT 支撑**。拿来只能当"展示文案"，无法评估对错——
   那会退回到"看着顺眼"的老路。
3. **复刻的目标是形态，不是内容**。参考视频真正值得复刻的是**结构**
   （冻结表 + 查表 + 状态机去抖 + 手-区域关联 + 四卡片 + 三轨），
   而我们已经把这套结构全部搭起来了（sop_steps.json / stations.json / App.vue）。

**但要向参考视频"抄"三样东西（这是 Codex 建议里最有价值的部分）：**

| # | 从参考视频抄什么 | 落到我们哪里 | 状态 |
|---|---|---|---|
| 1 | **兜底类的写法**：「流程外或插入式局部处理」「循环外停留与准备」比 idle/unknown 更专业 | `sop_steps.json` 的 fallback_steps | ⬜ 待做（改 JSON 即可） |
| 2 | **描述句式**：SOP 名 = "动词 + 物件 + 目标位置"（"取得带线壳体并落座夹具"） | 六步名可润色，但**必须保持与 GT 行为一一对应** | ⬜ 待你确认 |
| 3 | **left_hand 结构化**：`{action, holding, target}` 三字段 | segments 契约 | ⬜ 待做（发布层 + 卡片层小改） |

## 四、采纳决定（合并两边的方案）

**共识（两边独立得出同样结论，置信度高）：**

```
标准 SOP = 冻结表查表（模型永不生成）
当前动作/左右手 = 模型或学生模型预测
边界 = 本地时序逻辑（VLM 不猜边界）
```

**执行清单（按优先级）：**

| # | 事项 | 成本 | 归属 |
|---|---|---|---|
| 1 | **跑 multi 模式真实 API**（11 段 × 全局+左右手放大图）——验证"物件证据"能否把 18.2% 拉起来 | 11 次调用 | 用户执行（有 Key） |
| 2 | fallback_steps 改成参考视频式写法（流程外/循环外两类） | 0 | DSH |
| 3 | segments 契约拆 `{action, holding, target}` 结构 | 0 | DSH |
| 4 | 状态机去抖（连续 N 帧才切换 + 最短段长）——Codex 第 5 点，我们尚未做 | 1~2 天 | DSH（P3 前置） |
| 5 | 删除/归档遗留脚本 `run_video.py`（避免再次误导后来的协作者） | 0 | DSH |
| 6 | 学生模型训练（用原型标签 + multi 证据 + GT） | 2~3 天 | P3 |

**我不同意 Codex 的一点**：它把"SOP 体系没与参考视频统一"列为第一阻塞点。
经本文 §二 裁决，**词表统一不是必要的**（产品不同），真正的第一阻塞点仍是：
**物件证据不足**（multi 未跑）+ **状态机缺失**（去抖/合并未实现）。
这两件分别对应清单 #1 和 #4。
