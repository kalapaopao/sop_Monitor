## 一、先认错：我之前的判断有一处是错的

我上一轮用「闭集 6 选 1 = 18.2%」来论证"大模型不行"。**那个数字衡量的是"从固定表里选对类别"，不是"给一段动作起名字"。**

这两件事完全不同：

| 任务 | 大模型表现 | 依据 |
|---|---|---|
| 从固定 6 类里选对 step_id | **差**（18.2%） | 本项目 `run_teacher_per_segment.py` 实测 |
| **用自然语言命名一段动作** | **好** | 参考实现的输出就是证明（本文件第二节） |

所以正确说法是：**大模型不是分类器，它是命名器。** 我上一轮把"命名能力"和"分类准确率"混为一谈了。

## 二、他们的输出结构（OCR 实证）

界面标题：`动作分割结果 · test2`
副标题：`周期工序 / 当前细动作 / 左手动作 / 右手动作 / 操作器件与目标`

### 2.1 他们有、我们没有的字段

| 字段 | 他们的样子（OCR 原文） | 我们现在 |
|---|---|---|
| 步骤**代码** | `S900` `S703` `NO00` `S305`（共出现 50 种写法，OCR 可能有误） | 只有 `step_id` S1–S6 |
| 步骤**名称** | `夹具内供小件与悬挂工具作业`、`取得黑色壳片并与银灰件靠合`、`圆端环状部位处理并暫放颅装件` | 固定短名（`取镜座组件`） |
| **时间范围 + 时长** | `S9 00:00.00 — 00:41.80  41.80 秒` | 有 start/end，无时长展示 |
| **每只手独立三件套** | `器件：手中深色小物件` / `目标：小物件上作处` / 可见性 | 只有一个字符串 |
| **可见性** | `可见`(219) / `遮挡`(13) / `不可见`(10) / `局部可见`(1) | 没有 |
| **未确认兜底** | `器件：未确认` / `目标：未确认` 占 5.9% | 模板总是填满，不给"未确认" |

### 2.2 他们的 SOP 名称词表（15 种，按出现次数）

```
32  夹具内供小件与悬挂工具作业
20  取得黑色壳片并与银灰件靠合
14  流程外或插入式局部处理        ← 与我们 sop_steps.json 的 unknown 同名
10  圆端环状部位处理并暫放颅装件
 8  循环外停留与准备              ← 与我们 sop_steps.json 的 idle 同名
 7  取得带线壳体并落座夹具
 5  黑色手扌寺器朝向工件表面
 4  预裝件与壳体汇合及线状部位整理
 3  组合件移出并放到后方承接面
 3  候选周工序
 1  取得本次银灰带筋件并建立持握
```

### 2.3 他们的「当前动作描述」样例（这才是质量感的来源）

```
工人停在台前，左手局部可见且无明显操作
左手托稳目标，右手保持杆状物进行连续细小操作
左手微转并重新托持小物件，右手在其上端配合调整
双手在指端交会处持续细小捏动
双手分别搭在工作台前缘和后方边缘，持续停留并间歇
恢复注视手中区域，右手微调物件上端，左手支撑
```

**注意这些句子的共同点**：主语是"哪只手 / 双手"，谓语是具体动作（托稳 / 保持 / 微转 / 捏动 / 捏拨），宾语是"手里的东西 / 作用目标"。**它们描述的是双手协作关系，不是"这是什么工序"。**

### 2.4 他们的计数面板（状态机是明写的）

```
放钉关联紧固计数
· 新放钉 + 同次工具作业，合并重复下压
· 等待下一次可辨认的放钉与紧固动作
· 工具单独下压、抬起或手部按位不直接计数
```

这是把**规则本身显示给用户看**。可信度直接来自"规则可见"，不是来自模型多强。

## 三、必须说清的三件事（不是找借口，是事实边界）

1. **他们的词表是另一个产品的。** `黑色壳片 / 银灰带筋件 / 线状部位 / 夹具 / 承接面`——不是我们的 `镜座 / 上盖 / 密封塞`。这说明他们的 SOP 名称来自**该产品的工艺文档**，模型只是在文档范围内做命名。
   → 对我们的含义：**我们的 `configs/sop_steps.json` 需要一张更细的词表**，否则再好的命名能力也只能在 6 个粗名字里绕。

2. **他们的"质量高"里有相当一部分是"敢说未确认"。** 器件未确认只占 5.9%，但确实存在；而我们的模板**永远填满**。在演示里"填满"看起来更漂亮，在产线上"填满"就是漏报。

3. **两个同名兜底词（`流程外或插入式局部处理`、`循环外停留与准备`）与我们 `sop_steps.json` 完全一致。** 这两个词最早来自我们对参考视频的 OCR 记录（`docs/给我看的文档/05-参考视频SOP描述OCR记录.md`）。所以这段演示很可能与我们看的是**同一套参考素材**。这不改变它做得好的事实，但说明"词表"不是他们独创的。

## 四、可落地的结论：命名交给大模型，但代码要稳

他们的做法本质是：

```
稳定代码（S703 / NO00）  ← 程序内部用，不漂移
     +
描述式名称（取得黑色壳片并与银灰件靠合）  ← 每次可以用模型重新生成
     +
时间范围 + 时长          ← 可核对
     +
每手 {动作, 器件, 目标, 可见性}  ← 结构化，可审计
```

**这正是我们应该抄的东西**：不是"用大模型做识别"，而是"**用大模型生成显示名，用固定代码保证不漂移**"。

### 4.1 字段契约升级（建议）

```jsonc
{
  "step_id": "S3",                    // 稳定代码，程序用
  "code": "S303",                     // 段级代码（本段第 3 个 S3）
  "name": "组装镜座上盖",              // 固定短名，查表
  "name_display": "双手对位上盖并压合到位",  // ← 可由 VLM 每次重写，只是显示
  "start": 43.3, "end": 50.5, "duration": 7.2,
  "action": "双手将上盖对位并压合",
  "left_hand":  { "action": "扶稳镜座并对位", "device": "镜座组件", "target": "装配区", "visibility": "可见" },
  "right_hand": { "action": "压合上盖",       "device": "上盖",     "target": "镜座",   "visibility": "局部可见" },
  "visibility": "局部可见",
  "state_change": "inserted",
  "confidence": 0.82,
  "need_review": false
}
```

### 4.2 需要跟着改的三处

| 位置 | 改动 | 风险 |
|---|---|---|
| `scripts/enrich_segments.py` | 增加 `device/target/visibility/duration/name_display` 字段；本地模板允许输出"未确认" | 低（只加字段） |
| `web/src/App.vue` 四张卡片 | 左右手卡片显示 `器件 / 目标 / 可见性` 三行小字 | 中（改模板） |
| `configs/sop_steps.json` | 每个步骤补 `name_display_template` 与 `code_prefix` | 低（只加字段） |

## 五、仍然卡住的那一步

**命名层要用大模型才做得出第二节 2.3 那种句子，而环境里没有 `DASHSCOPE_API_KEY`。**

我这边的 `scripts/enrich_segments.py` 已经实现了 `--provider qwen`（含字段 schema、物件白名单、禁止改 step_id/边界、`consistent` 复核字段），缺 Key 时直接报错退出，不会伪造。

一旦有 Key，最小验证实验（半天、几十次调用）：

1. 取我们的 65 段里被判为 S1/S2/S3/S4 的那些
2. 每段给：段内 2 帧 **手周裁图** + 段的粗类 + 时间 + 六步表 + 物件白名单
3. 要求按 4.1 的 schema 输出（只填 `action / left_hand / right_hand / state_change / evidence`，**不许改 step_id 和边界**）
4. 人工抽查 20 段，看能否达到第二节 2.3 的句子质量

**这才是"大模型该做的事"的验证。** 我之前拿 18.2% 去否它，是拿错了考场。
